CATALOG DATABASE DERIVED PERMISSIONS - SECURITY REVIEW / CORRECTION PROPOSAL
2026-11-06. Draft for security/contract review; production acceptance remains OPEN.

Evidence and disposition
The operator reports APPROVED_PRESENT CONNECT and VIEW DEFINITION; UNEXPECTED
VIEW PERFORMANCE DEFINITION and VIEW SECURITY DEFINITION; ALLOWLIST_ABSENT both
column encryption/master-key definition permissions; matching role contract, no
duplicates, diagnostic exit 2. Both unexpected names were traced to the approved
AiCaseDataCatalogVerifier database VIEW DEFINITION grant via the live built-in
hierarchy. These are supplied observations, not independently rerun production
measurements. Exit 2 identified a verifier-model mismatch; it is not readiness.

Microsoft's database permission table explicitly lists VIEW DEFINITION as the
covering database permission for both names. Its metadata visibility guidance
explains their use at the applicable metadata scope. References reviewed:
https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-database-permissions-transact-sql?view=sql-server-ver17
https://learn.microsoft.com/en-us/sql/relational-databases/security/metadata-visibility-configuration?view=sql-server-ver17
https://learn.microsoft.com/en-us/sql/relational-databases/system-functions/sys-fn-builtin-permissions-transact-sql?view=sql-server-ver17

Security assessment
- VIEW PERFORMANCE DEFINITION permits performance-related definition metadata at
  database scope. Catalog information can reveal structure and implementation
  details useful for reconnaissance. It is not VIEW DATABASE PERFORMANCE STATE,
  VIEW DATABASE STATE, SHOWPLAN, SELECT on application tables, or authority to
  execute business procedures; none of those permissions is accepted by this fix.
  Do not infer access to every DMV or runtime query/plan surface from this name;
  each surface retains its documented permission requirements.
- VIEW SECURITY DEFINITION permits security-related definition metadata. This can
  reveal principals, permission relationships and security configuration, including
  facts that help an attacker map defenses. This visibility is sensitive even
  without business-row access. It grants no right to change grants, impersonate,
  alter policy, bypass RLS, or read credential secrets/password hashes. No
  stronger credential/cryptographic authority is added.
- The existing database VIEW DEFINITION already authorizes broad definition
  visibility, including source that may contain sensitive embedded literals. The
  two effective children expose subsets of that approved metadata authority; the
  proposed verifier change does not create new database authority. This conclusion
  depends on the exact existing role/token/direct/public restrictions and the
  demonstrated hierarchy, not on names alone. Catalog output and credentials
  remain restricted operational material under existing secret-safe handling.
- Retain VIEW DEFINITION: complete definition/dependency attestation relies on it.
  Removing it or substituting the narrower children could hide required catalog
  evidence. The review establishes no need to change the approved role design.
  If the owner no longer accepts this broad metadata visibility, redesign and
  re-attest separately; do not add DENYs to silence this diagnostic.

Proposed implementation boundary
Provision-ShaleAiIdentities.ps1 adds Get-CatalogDatabaseDerivedPermissions only to
Verify-Login's AiCaseDataCatalogVerifier DATABASE check, after the unchanged actual
contained-authentication and exact token checks. It re-reads ALL catalog-role
permission edges through the already-authorized admin connection and compares
against all six pinned entries, including state, class, securable, zero minor ID
and dbo grantor. The exact plain database VIEW DEFINITION grant must occur once.
The pinned JSON digest and all 324 role-contract edges remain unchanged.

The helper requires exactly one live DATABASE hierarchy row for each named child,
with covering_permission_name exactly VIEW DEFINITION. Missing, duplicate, NULL,
wrong-scope, cyclic, changed-parent or query-failure evidence stops. There is no
recursive acceptance of other children, CONTROL ancestry, server-level inference,
or blanket acceptance based on an effective VIEW DEFINITION name. Only these two
names are conditionally added to this identity's DATABASE evidence allowance.
The other identities, SYSTEM/OBJECT/COLUMN permissions and exact EXECUTE closures
remain unchanged. Explicit child grants would change the role contract or violate
the existing direct/public checks and remain rejected. Database duplicate evidence
now explicitly stops, complementing existing duplicate-sensitive object checks.

CONNECT remains required for all identities; VIEW DEFINITION remains required for
the catalog identity. Both named children are tolerated only after the derivation
proof, without making their presence a new requirement. The two encryption-key
permissions remain optional allowances under the existing public/effective evidence
contract. Zero, one or both may be absent; no grant, role edit or mandatory-set
expansion is justified by ALLOWLIST_ABSENT. Any unrelated permission still stops.
