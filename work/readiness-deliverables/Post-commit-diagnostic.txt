Finding and limits
- Operator reports committed provisioning, runtime full verification PASS, then
  POST_INSTALL_VERIFY failure. The fixed identity order makes catalog verifier the
  next sequence. However, success is printed before connection disposal: runtime
  Dispose could also have thrown before catalog began. Bootstrap has not completed
  verification. Do not infer a pass or assume the failed identity from stage alone.
- SQL_USER/DATABASE authentication and exact direct role memberships are necessary
  but do not establish actual contained login, own-session evidence, original name,
  exact effective token, effective permission closure or column authority.
- A definite observability defect is established: the original outer catch discarded
  every inner verification location. Neither a security discrepancy nor a defective
  acceptance predicate can be established from that output alone.
- Permission-List checks for unexpected effective rights; separate checks require
  database CONNECT, catalog VIEW DEFINITION, dependency-catalog SELECT and exact
  application-object permission equality. Same-Set compares sorted lists including
  multiplicity, not mathematical sets. Duplicate permission rows could therefore
  cause a mismatch; no production row-shape evidence currently proves this happened.
  Do not remove duplicates or expand allowlists speculatively.
- Catalog object rights remain VIEW DEFINITION, plus SELECT only on
  dbo.AiCaseDataDeployment, dbo.AiDataUnicodeRange, dbo.AiDataUnicodeLower,
  dbo.AiDataWordTransition. No catalog application EXECUTE is allowed. No additional
  permission, including derived platform permissions, is approved by this change.
- Every object column is independently checked with HAS_PERMS_BY_NAME for SELECT
  and UPDATE. Reference columns require SELECT=1. UPDATE=1 is always forbidden;
  SELECT=1 on any other column is forbidden. Existing invisible-object/NULL handling
  relies jointly on the complete dbo grant graph and empty object allowlist.
  Error 15151 is accepted only for OBJECT scope with an EMPTY allowlist. The catalog
  verifier has a nonempty object allowlist, so it never takes that exception fallback.
  All those acceptance conditions are retained, including required-evidence failures.

  BOOTSTRAP, object/column ordinals, numeric permission counts and fixed permission
  bits NULL/ZERO/ONE/OTHER to the existing sanitized stop message.

Checkpoint interpretation
- CONNECT: connection creation, SqlCredential assignment or actual Open failed.
- IDENTITY_QUERY / INDEPENDENT_IDENTITY_QUERY: own-session/independent catalog query.
- IDENTITY_ROW_ASSERT / IDENTITY_ASSERT: missing or mismatched actual identity proof.
- TOKEN_QUERY / TOKEN_ASSERT: query error or effective-token discrepancy.
- DATABASE_PERMISSIONS / SYSTEM_PERMISSIONS / OBJECT_PERMISSIONS: QUERY distinguishes
  unavailable evidence from ASSERT with unexpected/multiplicity counts.
- DATABASE_REQUIRED / SYSTEM_REQUIRED / OBJECT_REQUIRED: required evidence missing
  or exact object-list mismatch. Keep the approved allowlist; investigate metadata.
- OBJECT_INVENTORY / COLUMN_INVENTORY: dbo metadata enumeration failed.
- COLUMN_QUERY / COLUMN_ASSERT: per-column evidence unavailable or rejected.
- EXECUTE_SET: the complete required six-EXECUTE set differs (zero for catalog).
- CONNECTION_DISPOSE: checks succeeded but closing that connection failed after its
  success line. A prior body failure keeps its original checkpoint during cleanup.
- COMPLETE: that identity's complete sequence passed, not readiness/activation.

Local metadata correlation, only if an object/column checkpoint fails
- Object and column are ONE-BASED ordinals, not physical IDs. Zero means not entered.
  Hold the same catalog change freeze used for verification; drift invalidates mapping.
- Using an existing approved dbo SSMS connection, locally identify the object at the
  reported ordinal from this metadata-only list. Do not export the names/results:
    SELECT ROW_NUMBER() OVER(ORDER BY s.name,o.name) ObjectOrdinal,
      o.object_id ObjectId,s.name SchemaName,o.name ObjectName
    FROM sys.objects o JOIN sys.schemas s ON s.schema_id=o.schema_id
    WHERE o.is_ms_shipped=0 AND o.type IN('U','V','P','FN','IF','TF','SN','FS','FT','PC')
    ORDER BY s.name,o.name;
  For the identified object, enumerate sys.columns WHERE object_id=<local ID>,
  ORDER BY column_id. The diagnostic column ordinal is the position in that list;
  physical column_id can have gaps. Keep catalog names local to approved review.
- Do not use EXECUTE AS to replace the actual contained authentication proof.
  Review the exact failing existing query/expected rights through approved actual
  credentials, retaining only bounded counts/bits. No protected data SELECT is needed.
  Distinguish a query/metadata-visibility failure from a successful query returning
  excess/missing authority, then compare with the unchanged role contract and grant
  provenance under dbo visibility. An extra effective permission remains a STOP even
  if its origin is an implicit permission hierarchy rather than a direct new grant.
- A duplicate-only list mismatch warrants investigating fn_my_permissions row shape
  and PowerShell result handling against the supported engine/shell. It is not proof
  of a security discrepancy, nor permission to deduplicate, bypass or broaden checks.
  If the bounded checkpoint cannot settle the cause, prepare a separate narrowly
  sanitized diagnostic for that checkpoint; never request/export raw exceptions.
