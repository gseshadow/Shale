Output and interpretation
- APPROVED_PRESENT and UNEXPECTED preserve occurrence counts. ALLOWLIST_ABSENT has
  occurrences=0. Absence is informational unless required by the unchanged verifier;
  the diagnostic uses exit 2 for any allowlist absence, excess or duplicates so an
  operator must review the complete difference, without changing acceptance rules.
- SUMMARY always says acceptance=NOT_VERIFIED and controls=OFF. Exit 0 means only
  no database-list/role-edge difference was collected, not full verification/pass.
  Exit 2 means evidence was collected and a mismatch exists. Exit 1 means evidence
  acquisition, authentication, validation, drift or cleanup failed. DIAGNOSTIC_STOP
  contains only a fixed checkpoint and mutation=NONE/controls=OFF. Never infer a
  permission is safe from successful collection or a hierarchy explanation.
- ROLE_CONTRACT compares all catalog-role permission edges, minor IDs and grantor
  against its six pinned edges. It reports a boolean without exposing object names.
- PROVENANCE enumerates every matching database grant/deny along the effective
  permission's same-class covering chain. DIRECT uses a user edge; INHERITED uses
  the verified catalog role or public. The _HIERARCHY suffix means a covering grant
  implies the reported permission. Paths run from effective child toward covering
  ancestor. GRANT_WITH_GRANT_OPTION is retained, never normalized to plain GRANT.
  DENY is reported as contrary evidence, never counted as a grant route. Multiple
  routes are retained; the diagnostic does not choose a supposedly unique cause.
- HIERARCHY records the live engine's transitive DATABASE covering chain.
  UNRESOLVED means no granting edge was found in that chain. Do not conclude an
  unexplained permission is harmless/platform-provided. Fixed-role/server/ownership
  explanations outside this model require separate review; the exact contained
  token disallows extra/fixed/nested roles. No server hierarchy is assumed applicable
  to this contained user and no server permission probe is used.
- Grant and effective-permission reads are repeated, as are identity/token proofs.
  Grant/effective disagreements stop at DRIFT; repeated identity failures retain
  their original checkpoint. These are sampled checks, not an atomic snapshot;
  the operator change freeze is still required. The role-contract comparison is a
  separate sampled read. Do not infer that intermittent or concurrent changes were
  excluded merely because the two samples match.
