## Finding and scope

Base: explicitly refreshed `origin/codex/latest` = `684ab9d638e326ec52451a834fb85158def10197`.
Application compatibility pin: `59d8374858764788c621f6f8d986773b58ab79c4`.

Current `SqlRememberCredentialStore` already uses explicit UTC and the bounded V2 resolver; it is
unchanged by this fix. The remaining current defects are in `UserSessionDao` and
`SessionManagementService`, whose pre-fix code matches the application pin. The sandbox's old remembered

into the current application build.

The supplied Windows 547/23000 report establishes a constraint violation but does not name it.
The isolated SQL Server reproduction establishes **CK_UserSessions_Refresh**, from the SQLException
chain of the actual restore controller/JDBC operation. The pinned rotation fails at line 46.
`LastRefreshedAt` receives Denver local calendar fields from `setTimestamp(Timestamp.from(now))`,
while `IssuedAt` was generated by `SYSUTCDATETIME()`. A restore minutes after issuance therefore
tries to persist a refresh six hours before issuance in October. The serializable rotation rolls
back; neither credential hash nor access JTI is committed. The expiry constraint is not the
constraint failing in this reproduction. Revocation uses database UTC and an approved reason;
it is not the failing assignment. No constraints/defaults/grants/RLS are changed.

The supplied `ExpiresAt=2026-11-18 12:58:30.5985117` is consistent with binding a deadline near
`19:58:30Z` in Denver at that **future deadline's** UTC−7 offset. October 19 is UTC−6; November 18
is UTC−7. It is not evidence that the JVM changed its default between issuance and restore.
Source searches of current and pinned application code found no `TimeZone.setDefault` or
`user.timezone` override. The actual Windows JVM settings/history were not remotely inspected.

Reading is equally important: `getTimestamp()` interprets zone-less SQL UTC fields in the JVM
zone, moving October `IssuedAt` six hours into the future. An expiry written and read with the
same local zone may appear to round-trip while SQL expiry comparisons remain wrong. Changing
JVM zones across launches changes that accidental behavior. UTC calendars are now explicit for
the remaining Instant writes and reads in current `UserSessionDao` and session-list/admin-since
projections in `SessionManagementService`, plus the pin-only compatibility remembered store. Current
remembered-store UTC handling, V2 lookup, input/cardinality validation, timeout and sanitization remain unchanged. A fresh mutable Calendar is used each call.
The SQL UTC defaults and refresh/revocation expressions remain authoritative. Business-local
case/task/calendar dates, application-wide timezone and user-facing date formatting are unchanged.
Existing shortened expiries remain shortened; this change never repairs or extends their values.

Audit review: credential lookup/rotation remains authentication plumbing in the existing durable
session boundary. Existing transactional self/admin/logout security audits are unchanged. No new
audit schema/event or secret/hash payload is introduced.

## Session recovery decision

The pinned desktop writes a protected `v1\nA\nB` pending record before sending A→B. After a 500
rollback, SQL still holds A. On Retry it first tries B→C (401), then falls back to A→B (500), but
has already saved `v1\nB\nC`. That explains the reported 401/500 sequence and can lose A locally.
This task does not rewrite that client protocol or fabricate the missing secret from a hash.

* If the original valid pending pair survives, one controlled startup with the corrected API may
  restore it. Observe the outcome once; no repeated Retry or manual request replay.
* After the reported 401/500 pair, assume the saved pending state may no longer contain the valid
  credential. Preserve its archive and original failure evidence, choose the supported password
  sign-in path with “Stay logged in” checked, and use the existing synthetic account/password.
  This creates a new remembered session through normal enrollment and replaces the live protected
  file through the application's normal protected save. The archived pre-recovery ciphertext,
  installation identity and old SQL row remain retained. Never delete/edit the credential manually.
* If preserving the live protected file at its original pathname is required, stop before desktop
  startup/password sign-in; API verification alone can proceed. Normal remembered login necessarily
  writes the live protected file. Do not claim that file remains unchanged after recovery.
* Check protected-save success, ordinary close/reopen and restore success. Then test explicit logout
  only after the evidence archive exists; logout intentionally clears the **new** live credential
  through the supported application path and durably revokes its session. Confirm subsequent access
  is rejected. Old failed-session history is retained; use the supported My Sessions revoke action
  for the exact old session if required, never SQL DELETE or timestamp edits.
* Any new 500 or unexpected 401 stops acceptance. Retain logs/status, timezone/JDK identity and
  read-only SQL evidence. No timestamp repair, constraint bypass, global timezone override or New.

Manual recovery timing / retirement acceptance is still **NOT MEASURED**. No installed MSI or
production serving artifact acceptance is inferred from this source compatibility build.
