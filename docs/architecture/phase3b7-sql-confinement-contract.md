## Credential proof decision

Exactly two proof designs are considered:

| Consideration | A Raw ACCESS hashed inside SQL | B Existing ACCESS digest computed in application |
| --- | --- | --- |
| Security benefit | Stored digest theft alone cannot invoke the new data procedures. SQL verifies possession of the original high-entropy opaque value. | Preserves current hash-only JDBC flow. A database digest leak now enables invocation, so digest confidentiality is an explicit boundary requirement. |
| JDBC and SQL exposure | Original OAuth bearer crosses JDBC/TDS and SQL execution memory. A leak may also authenticate at MCP. | Only a 32-byte digest crosses JDBC/TDS. It is independently sufficient at this SQL boundary and must receive bearer-secret protection. |
| Memory lifetime | Raw header/token plus driver and SQL copies must survive invocation and final gate. Immutable Java Strings cannot be reliably erased. | Raw header lifetime stays at authentication; a separate mutable digest holder survives bounded invocation and cleanup. Driver and SQL copies still cannot be guaranteed erased. |
| Diagnostics and logging | Parameter tracing, exceptions, dumps, proxy/APM interception can reveal original ACCESS. | The same mechanisms can reveal a SQL bearer digest. Calling it a hash never permits logging it. |
| SQL parameter capture | Parameter/RPC capture exposes raw bearer. | Parameter/RPC capture exposes SQL bearer; parameterization prevents injection, not disclosure to privileged tracing. |

**Choose B.** ACCESS already has at least 256 bits of entropy; hashing adds no password-guessing weakness. B avoids expanding raw OAuth bearer exposure, fits existing issuance/validation digests, and requires less new token handling. Its security depends on preventing digest enumeration and privileged diagnostic disclosure. Those are acceptance conditions, not assumed protections. Neither design makes a compromised SQL administrator harmless; both are adequate under the restricted-principal and diagnostic boundaries specified here. No asymmetric signing is introduced.

`ProofDigest` is exactly the existing digest algorithm/byte encoding used by `AiOAuthCredentialStore.digest`; no new salt, normalization, double hashing, or alternate token format. Bind as binary bytes through prepared RPCs, never SQL literals or hex Strings. SQL input type is `varbinary(max)` with an exact `DATALENGTH=32` check before conversion to `binary(32)`; a fixed-width parameter must not silently truncate a longer input. Unknown, malformed, wrong-kind, or foreign-deployment proof gets the same safe authentication failure.

Keep `VerifiedIntegrationContext` immutable and credential-free. Introduce a separate internal, redacted, nonserializable `AutoCloseable` proof holder with no byte-array getter, equality dump, logging, audit, MDC, exception, or DTO propagation. It owns a defensive mutable copy and permits only controlled statement binding. Share its lifetime explicitly with the bounded invocation, not ThreadLocal/AppState/servlet persistence. Clear buffers and parameter references in `finally` after final gate **and bounded failure/release cleanup**, then close the holder on every outcome. Cancellation must not clear it before required cleanup can authenticate. No persistent positive authorization cache; operational invocation records below never replace fresh proof and live checks. Document that Java zeroing cannot erase all driver, heap-dump, or SQL copies.

Require encrypted, certificate-validated JDBC; disable/redact SQL bind logging, JDBC tracing, request/header dumps, APM argument capture, RPC/Extended Events parameter collection and diagnostic dumps for this path. The AI identity has no tracing/server-state privileges. Authorized diagnostic capture and incident handling must treat captured digests as credentials. No digest appears in audit, telemetry, receipts, snapshots, response serialization, or the new invocation ledger. Stored credential digests remain available only to existing credential lifecycle authority and confined module internals.

## Dedicated principal and pool

Proposed application accessor: `DataSources.aiCaseData()`. Proposed configuration: `shale.ai.data.jdbc-url`, `.username`, `.password`; independent secret provisioning and rotation. No defaults or fallback to RT, OAuth bootstrap, setup, operator, or admin credentials. Separate Hikari pool instance, connection factory, lease initialization, metrics names, and close lifecycle; identical server/database is permitted, identical credentials or security identity is not. Data authentication, both Case handlers, failure accounting, quota cleanup, and final handoff all use this identity. A separate bounded cleanup pool may use the same restricted AI identity; it cannot borrow ordinary runtime authority.

The database user belongs only to `public` plus `AiCaseDataRuntime`. It cannot own schemas/modules/roles, impersonate, change grants or policies, or obtain server privileges. It is not in `AiIntegrationRuntime`, `AiIntegrationBootstrap`, `AiCapabilityOperator`, `ShaleAdmins`, `db_owner`, `db_datareader`, `db_datawriter`, sysadmin, or any nested/custom equivalent. Membership restrictions apply to effective server and database tokens, including group identities. Existing ordinary/issuer/bootstrap roles and credentials remain unchanged; the AI data call graph must never reach them as an application fallback.

Before registering either enabled data handler, and on every pool rebuild/credential rotation, startup must:

1. Refuse missing/incomplete AI datasource or failed connection/attestation. Keep packaged flags OFF. No partial handler readiness.
2. Compare configured identities and actual SQL login SID, original login, database principal and effective tokens with ordinary runtime, bootstrap, setup/operator/admin identities. Resolve aliases/case/group mappings; configuration-string inequality is insufficient. Equal or unverifiable identity fails closed.
3. Verify current database, canonical issuer/resource binding, migration/source/catalog receipts, exact role memberships, module bodies/owners/call graph, RLS/trigger states, and effective permission allowlist. Include public and nested roles, server grants, column grants, ownership, synonyms, views/functions, cross-database routes, and grant options. Reject excess effective authority even when a direct grant is absent.
4. Prove the six object EXECUTEs below and the required negative capabilities as the actual AI login. Ordinary harmless system connection/context facilities are enumerated separately; `sp_set_session_context` being callable does not grant data authority.

Use a deployment verifier under separately governed read-only catalog authority for catalog facts not visible to this principal, tied to the live AI login SID/token and current catalog revision. Startup must verify its current attestation, not accept a stale unchecked file. An incomplete metadata view is not evidence of no grants. A controlled permission/catalog change drains and reattests pools before readiness; unexpected drift removes readiness. This is verification only, never a startup installer or auto-grant mechanism.

There is no public generic Case SELECT, PHI append, audit append, quota reservation, credential resolver/list, admin review, issuer, or control procedure.

Common parameters: `@ProofDigest varbinary(max)` required on every call; `@InvocationId uniqueidentifier` and `@CorrelationId uniqueidentifier` are server-generated UUIDs, never JSON-RPC IDs. A database-bound invocation record makes UUIDs references only. No authoritative tenant, actor, integration, grant, session, credential ID, client ID, scope mask, policy revision, SQL, field list, sort, result IDs, or audit parent is accepted from the caller.

### Database invocation binding

Add a protected `AiCaseDataInvocation` operational table, not a credential or authorization cache. Key is globally unique InvocationId. Store immutable derived tenant/user/integration/grant/session/ACCESS-row ID, correlation, canonical deployment binding, initial scope/revision ceiling, first DB admission time and deadline; bind operation and bounded page/requested ID on first dispatch. Store monotonic lifecycle facts for dispatch claimed, reservation, READ committed, failure stage and handoff consumed. Do not store query/query hash, Case projection, digest, raw ACCESS, arbitrary metadata, or duplicate audit events. Bound nullable search page/requested ID are the same typed diagnostic references as existing audits. Strict tenant FILTER/INSERT/UPDATE BLOCK, tenant-qualified noncascading ownership FKs, immutable-owner/monotonic transition enforcement, and no direct role access are required. Retain records under the governed accounting/history policy; no purge is added.

Authentication creates the record only after live proof validation. Subsequent calls prove the exact same ACCESS digest again and compare the resolved credential/lineage, correlation, scope/revision ceiling and invocation binding. A new valid B proof cannot claim A's invocation; another token of A's session cannot substitute for the bound ACCESS row. Concurrent or repeated dispatch cannot perform another Case read or append another success. A committed READ-stage failure also makes the invocation ineligible for later Case dispatch; failure recording cannot prepare an invocation for a subsequent unaudited read. A rejected/retried invocation never replays a stored protected result. A caller with a valid bearer may start a genuinely new invocation, charged under existing quotas.

First authentication clamps the supplied deadline to the earliest live authority deadline and DB UTC + 10 seconds. Later calls can only shorten it. Java retains the original earlier monotonic transport-admission deadline, covering work before authentication; caller dates can never extend SQL's bound. Records do not assert network delivery or attest that an untrusted SQL client generated a UUID randomly. They prevent rebinding/replay; possession of valid proof remains the authority. Authentication/discovery alone consumes no Case quota; unchanged discovery/edge limits still apply. Failure recording can create a historical-only record where authenticated dispatch failed before this record existed.

## Authority validation and transaction ownership

Every live operation authenticates one exact ACCESS digest and derives all identities from immutable credential lineage. Require canonical issuer/resource from deployment configuration, Kind=ACCESS, unconsumed/unrevoked credential, current generation rules, matching delegated family, consumed non-denied authorization transaction, original live WEB session, consent timestamp, grant, registration, optional original confidential key, eligible current Users (`is_deleted`/`IsRemoved`), active tenant, global epoch, tenant policy, registration/grant revisions and current scope intersection. No legacy nullable-lineage family qualifies. Enforce the minimum credential/session/idle/grant/registration/WEB/key/invocation deadline, key ValidFrom and no expiry skew. Scope is credential AND session AND grant AND registration AND initial invocation ceiling AND supported bits; revalidation can only narrow. Reductions or revision mismatch fail closed as today.

All public procedures require `@@TRANCOUNT=0`, implicit transactions OFF, no ambient caller transaction, bounded lock/statement deadlines, XACT_ABORT and complete TRY/CATCH rollback. Reject nested transactions; never COMMIT a caller transaction. Java invokes with autocommit enabled and must not recreate the old Java-composed read transaction. Public procedures own their transactions. Helpers cannot commit or expose intermediate results.

The lock protocol preserves existing `AiCapabilityV1` shared application lock, then proof-derived `AiTenantV1:<tenant>` lock (exclusive for quota/accounting/handoff transitions; shared for a read-only validation where safe). Held authority rows follow global capability → tenant policy → integration → grant → delegated session → user. After that prefix, acquire ShaleClients → AiAuthorizationTransaction → original UserSessions WEB row → AiIntegrationClientKey (when present) → AiOAuthCredential → AiCaseDataInvocation → AiQuotaReservation, retaining required locks to commit. Acquire these rows explicitly in order before any validation join so optimizer join order cannot introduce a later first lock. Preserve existing mutator conflict rules; verify this suffix against trigger cascades in concurrency acceptance. New invocation locks must not be acquired before the capability/tenant prefix. The preliminary owner lookup retains no locks before this prefix; it is provisional only. Re-read its proof mapping under held locks. All authority, quota and lifecycle lock waits finish **before** the decisive `SYSUTCDATETIME()` sample. Never validate expiry from a pre-wait Java or SQL timestamp. Mutators retain conflicting locks in the same established prefix order.

### Search operation

`AiDataSearchCasesV1` is one narrow callable database operation with **two sequential top-level transactions**, plus bounded failure handling. Atomic means the Case read and required success audits share the second transaction; quota must deliberately survive its rollback.

1. Authenticate proof, load/bind invocation and validate input before Case work. SQL independently checks normalized-query and page rules; no table query is possible on an invalid request.
2. In a short admission transaction, revalidate full live `cases.search` authority under locks. Claim dispatch once, reserve/account against existing `AiQuotaReservation` and commit. Search cost is 10. Throttle commits a zero-cost attempted call and returns no Case data. An invalid/forbidden pre-admission verified attempt is accounted through the failure path exactly once.
3. Start the read transaction; authenticate/revalidate proof, unchanged invocation ceilings and active admitted unreleased/unexpired reservation. Run one literal bounded Case-name search. SQL uses fixed reviewed expressions and bound parameters, no dynamic SQL. Fetch at most 11 internally, return at most 10; page 0–9, offset page*10. Exclude the probe from results/audit. `hasMore` reflects that authorized probe; `windowExhausted=(page=9 AND hasMore)`.
4. Insert one existing integration READ/ALLOWED_READ parent and exactly the 0–10 RETURNED children derived from the actual result. Verify persisted parent/children/cardinality, not just affected-row counts. Empty search still has one success parent and no children. No PHI success event for search, preserving its approved exemption.
5. Revalidate full live authority/expiry/scope/reservation at the in-transaction gate; commit success audit and invocation READ state together. Return only the minimized page and receipt after commit. Failure rolls back this transaction, never the already durable admission.

SQL input validation must match Java strip semantics, UTF-16 and Unicode letter/digit rules exactly: required normalized length 3–100 UTF-16 units, at least three Unicode letters/digits, no unpaired surrogates; page integer 0–9, fixed size 10. Do not substitute SQL LTRIM/RTRIM or collation-dependent character classes for Java semantics. Use private pure SQL functions and generated read-only Unicode mapping/range data pinned to the supported JDK behavior for whitespace, letter/digit classification and Locale.ROOT case mapping (including contextual or expanding mappings). Generate these build artifacts from the supported Java reference implementation, include them in the additive migration receipt, deny direct AI access, and exercise shared reference vectors. This is the chosen normalization implementation strategy; do not use SQL LOWER as a substitute where it differs. Any incompatibility blocks acceptance. Here `NormalizedQuery` means the Java-stripped, case-preserving literal. SQL verifies normalized equality and validates length/classification before lowercase expansion, matching the existing DAO entrypoint. Internally lowered/escaped bind text may expand under the pinned mapping; it is bounded by that mapping and never truncated. Query lowercasing uses the existing Java Locale.ROOT mapping and literal bracket escaping in the parity contract; SQL receives that normalized literal, performs the equivalent fixed transformation, and never treats `%`, `_`, or `[` as client wildcard syntax. No blank browse or generic selection branch exists.

### Overview operation

`AiDataGetCaseOverviewV1` uses the same independently committed admission transaction, cost 1 and required `cases.overview.read`. Search scope is neither required nor sufficient.

In its second transaction it authenticates proof again, derives durable authority, requires the bound active reservation and reads exactly one same-tenant, nondeleted minimized Case by positive int32 ID. Unassigned and closed Cases retain existing visibility. Missing, foreign and deleted targets produce identical `CASE_UNAVAILABLE`; do not look up foreign ownership to explain absence.

For the one authorized result, append exactly the existing PHI event using database-derived tenant/actor/Case and the current DAO constants: ObjectTypeId 1, FieldName `Case.Overview.Read`, FieldCode 4, StringValue `action=READ;screen=Case.Overview`, and NULL DateValue/BooleanValue/IntValue. Preserve the catalog-dependent FieldCode binding to the existing 4 value. The existing connection-bound `AuditLogDao.appendPhiWriteAudit` uses application local wall time for EntryDate; the new SQL implementation must convert its DB time sample into the explicitly configured existing application PHI-audit time zone and preserve the stored timestamp type/precision. The protected deployment configuration pins that zone and its SQL/Java mapping; parity tests cover DST transitions. Do not silently reinterpret this PHI field as UTC or accept a caller timestamp. Integration audit OccurredAt remains database UTC. The existing five-second audit timeout is a timeout, not a stored audit field, and remains clipped to the invocation deadline. Validate exactly one persisted PHI row (including suppression-trigger detection using the existing locked count-delta semantics), then one existing READ/ALLOWED_READ integration parent and one RETURNED Case child. Verify cardinality and persistence. Perform the full final in-transaction authority gate and commit all success facts together. Failure of read, PHI, parent, child, gate, or commit withholds every protected field. No public PHI append procedure exists. PHI row identity is not linked by invented timestamp/correlation metadata; preserve the current atomic-group guarantee.

The eight semantic fields remain `caseId`, `caseNumber`, `caseName`, `status`, `practiceArea`, `responsibleAttorney`, `primaryLegalAssistant`, `updatedAt`, including existing bounded nested relationship fields and required nulls. Internal flattened columns may reconstruct only those fields. Preserve stored-local updatedAt text, no UTC reinterpretation. Existing source guards reject oversized names instead of truncating; noncanonical status color retains the existing neutral-null normalization. No extra Case column, hydration, RowVer, audit value, probe, or hidden owner projection is exposed.

## Failure accounting without data authority

Historical ownership is proven by exact supplied digest equality with the retained unique ACCESS CredentialHash, plus immutable tenant/user/integration/grant/session/deployment lineage. The private lookup validates Kind and exact canonical issuer/resource and lineage even when expiry/revocation makes it unusable for reads. It never accepts credential IDs as proof. Failure/release additionally compare any existing invocation's immutable ACCESS-row binding and correlation. If digest/retained lineage is absent or inconsistent, no tenant attribution is possible: emit bounded sanitized aggregate security telemetry only. No fallback owner or ID-only failure attribution.

Expired/revoked/disabled proof may authenticate **historical ownership only** for these two procedures. They cannot SELECT Cases, test Case existence, append PHI, create ALLOWED_READ, renew a lease, reset scopes, or call a data helper. A valid syntactic requested ID is only REQUESTED, including a foreign ID, without a Case FK or existence lookup. Unknown proof cannot manufacture tenant history. Edge/process limits and the existing three-second independent cleanup budget bound failure traffic; retained proof ownership is not positive data authorization.

| Failure | Accounting and audit contract |
| --- | --- |
| Invalid input | No Case work. Exactly one zero-row-cost attempted call if not already reserved; INVALID_INPUT/INPUT READ parent, no returned children. Valid typed Overview target may be REQUESTED; malformed ID/page omitted. |
| Forbidden or expired/revoked authority | No Case work or handoff. With historically authenticated proof, DENIED/AUTHORITY and one call attempt if not already accounted. An admitted invocation retains its row charge. |
| Unavailable/missing/foreign/deleted Overview | Preserve admitted one-row charge, no PHI/success facts, UNAVAILABLE/CASE_UNAVAILABLE with syntactic REQUESTED only. |
| Throttled | Preserve durable rejected call with zero row cost, THROTTLED/QUOTA; process-limit rejection before SQL admission records one zero-cost call. No duplicate call when admission already recorded it. |
| Timeout | UNAVAILABLE/DEADLINE; rollback any active read, withhold output, preserve committed quota and any committed success, release concurrency through authenticated cleanup. |
| Cancellation | CANCELLED/CANCELLED; same rollback/no-refund rule. Temporarily clear thread interruption only for bounded failure/release cleanup and restore it. No detached Case work. |
| Audit failure or suppressed insert | Roll back Case/PHI/integration success transaction. Separate failure transaction records UNAVAILABLE/AUDIT when possible; never return data. Failure-audit outage emits only `INTEGRATION_ACCESS_AUDIT_OUTAGE`, no sensitive spool or reread. |
| Uncertain commit, close, or encoder failure | Withhold all output, retain possibly committed success and charges; no automatic read replay or audit deletion. Safe UNAVAILABLE with existing COMMIT/CLOSE/SERIALIZATION/OVERSIZED reason as applicable. |

`AiDataRecordCaseFailureV1` owns one short transaction after the read connection has been rolled back/closed or discarded. It serializes against in-flight completion, ensures an existing quota attempt is reused (otherwise inserts existing Admitted=0/RowCost=0 accounting), and appends only an existing failure outcome. SQL selects TERMINAL only when a matching committed READ/ALLOWED_READ exists; otherwise READ. Unique `(InvocationId,Stage)` and exact payload comparison make bounded duplicate cleanup idempotent; a conflicting duplicate is rejected, never overwritten. No new outcome/reason enum is invented. Caller failure reasons describe service observations, not cryptographic proof that an external event occurred; this principal cannot use them to claim a successful read.

`AiDataFinishCaseQuotaV1` independently proves historical ownership and releases only that invocation's concurrency. It never refunds calls/rows or marks handoff success. Repeated cleanup is a no-op; a released reservation cannot reenter a read or final gate. If cleanup cannot persist, existing lease expiry (at most 15 seconds) remains the crash backstop. Lost admission acknowledgement is resolved only for bounded failure accounting/release, never by retrying Case dispatch. An uncertain read COMMIT is serialized before deciding READ versus TERMINAL; if still unresolved within the short budget, withhold output and emit the fixed outage signal.

## Fresh post commit final handoff gate

After success COMMIT, complete procedure drainage and successful lease close, Java encodes exactly one private immutable bounded response and measures the complete envelope. Preserve search structured/full limits 32768/65536 bytes and Overview 8192/32768 bytes, original ten-second monotonic deadline, process admission limit five, cancellation checks and no partial result. No Case reread or hydration during encoding.

Immediately before the single internal buffer return, call `AiDataAuthorizeCaseHandoffV1` on a fresh short lease with **proof again**. Derive identity anew and verify the exact bound invocation, successful READ event, operation/scope, original ceilings, reservation and unconsumed handoff. Acquire capability and exclusive tenant/quota application locks, then the fixed authority-row prefix and remaining required locks. Revalidate global/tenant/integration/grant/session/user/tenant/credential, original WEB/key/authorization lineage and all revocations. Release concurrency and prepare the one-shot handoff state **before the final clock sample**, within the same transaction; validate the pre-release lease state/expiry. Sample database UTC after every possible authority/reservation/housekeeping wait, enforce earliest live expiry and invocation deadline without skew, then commit. On denial roll back the tentative handoff/release; separate cleanup can release afterward. Return no Case data, only the gate receipt.

Java records monotonic time **before** executing the gate. The permit uses at most SQL RemainingMillis minus elapsed time since that start, conservatively covering query, COMMIT acknowledgement, driver drainage and close; no clock conversion or cached prior receipt may extend it. A zero/expired permit, cancellation, connection-close failure or elapsed original deadline discards the buffer. There is no further queued work or network wait between permit check and internal handoff. Transport retains its existing deadline/size checks. No SQL transaction remains open during response transmission. Revocation committed before this gate denies; authorization linearized first may complete, with no claim of recalling already handed-off bytes. Committed ALLOWED_READ records server access, not delivery.

### Deterministic expiry acceptance

Retain #1919's red test until corrected production behavior passes the same expectation on both clients. A deterministic fixture must identify the final gate by exact invocation, procedure phase and actual SQL SPID; block a required lock after read/audit COMMIT and encoding but before the final clock sample. Use owner-only, explicitly labeled deadline injection for that exact bound session/credential/idle lineage, held stable through the observed gate. Prove with DMV/trace evidence that this SPID is waiting on that blocker and that database UTC has crossed the persisted effective deadline before release. Release within the unchanged lock/request deadlines. After unlock, capture the same gate's post-lock UTC sample and expired effective deadline, then require denial, zero protected bytes and one appropriate TERMINAL denial; the prior PHI/READ/RETURNED group remains committed.

Synchronize test phases with latches/barriers and positively observed locks, not sleeps or Java-clock assumptions. A fixture cannot rewrite idle expiry and then let another path refresh or replace it unnoticed; record row version, session ID and gate minimum-deadline inputs in test-only evidence without proof bytes. A timeout, wrong SPID, missing final-gate execution or unrelated SQL error is a failed/inconclusive drill. Add a positive control with a future deadline and negative controls for each expiry constituent, plus elapsed permit expiry during COMMIT/close. No production test hooks, pause parameters, schema changes to MCP, or weakened assertions.

## Case query ownership and parity

**Strategy B is the binding decision.** `CaseSummaryDao.selectMinimized` remains the ordinary Java query owner. The AI protected SQL procedures own their own minimized queries behind the confined database boundary. They cannot delegate Case selection to Java because that would require forbidden direct SELECT grants. Migrating ordinary desktop/REST callers onto OAuth-proof procedures would change ordinary authentication, transactions and search exemptions, exceeding this task. The previous blanket no-duplication recommendation is replaced by explicit semantic ownership and a mandatory parity suite.

Use one shared fixture/vector corpus and compare actual ordinary DAO results with protected SQL results under equivalent valid authority, for every overlapping behavior. Compare semantic DTO values including nulls and timestamps, not source SQL text. Cover:

- All eight fields, relationship selection/tie breakers, nullable/global/same-tenant lookups, responsible-attorney/assistant role semantics and tenant-qualified joins; no child hydration or extra fields.
- Eligible same-tenant actor and tenant; identical root nondeleted predicate; unassigned and closed Cases included where currently permitted; missing/foreign/deleted targets indistinguishable.
- Case name then ID ascending order, actual authoritative collation, equal names, null names and Unicode. Preserve existing status/assignment selection, not simplified joins.
- Java strip/Locale.ROOT behavior, supplementary characters, invalid surrogates, Unicode letter/digit classification and UTF-16 bounds. Exact escaping order is `[` to `[[]`, `%` to `[%]`, `_` to `[_]`; include quotes, semicolons, comments, SQL-looking names, wildcard decoys and non-ASCII case mappings.
- Page 0 and 9, size 10, size+1 probe 11, authorized probe exclusion, hasMore/windowExhausted and exact offsets. Ordinary larger page/size ranges remain ordinary-only.
- Source DATALENGTH bounds, reject-without-truncation behavior, neutral-null invalid color and stored-local updatedAt formatting, all existing byte-envelope boundaries, plus PHI timestamp/type and time-zone mapping compatibility.

## Remaining architecture risks and approval limits

- Digest theft enables replay at this SQL boundary until durable expiry/revocation; it is a bearer secret. Privileged SQL/host diagnostics and a compromised ordinary runtime/control plane remain separate trust risks. Principal separation confines the AI credential, not every process or database administrator.
- Exact Java Unicode strip/case/classification behavior needs a pinned SQL validation implementation and parity evidence; SQL collation shortcuts are insufficient. Bounded output does not bound scanned work; representative plans, tenant volumes and latency remain acceptance requirements.
- The private owner lookup is a deliberately narrow RLS exception. Its body/owner, static reachability, caller-context restoration and no-Case projection must be verified; a broad execute-as-owner replacement is outside this decision.
- Tenant-serialized locks preserve current quotas but limit throughput. Lock ordering, trigger cascades and all post-lock UTC samples require actual SQL concurrency evidence, especially the unresolved #1919 expiry root cause.
- Additional invocation state requires immutable bindings, idempotency, trusted receipt coverage and governed retention. It cannot silently become a token cache, data store, cleanup bypass or delivery assertion.
- Startup effective-grant attestation needs complete, current catalog visibility without expanding the data principal. Deployment must supply that verifier authority and drain/revalidation lifecycle before handlers become ready.
- Authoritative artifact recovery/hash gates, source versus deployed parity, TLS/proxy, complete client corpus/response boundaries, representative load, SDK prerelease approval and tenant/legal retention sign-off remain separate open gates from #1919/#1920.
